# T1 — UI & frontend ceiling

*The product's #1 weak spot ([weak-spot review](../audits/architecture-weak-spots-2026-07.md) §1): the scaffolded UI is excellent until the closed primitive set runs out, then customization is an all-or-nothing ejection. These missions raise the ceiling and soften the cliff.*

## M-T1.1 — Paged, sorted, filtered Table — `partial` · **L** · P1
The wire ships the `paged` carrier; no frontend consumes it. `Table`/`QueryView` fetch entire collections; no column sort, no interactive filter. Add pagination/sort/filter to the `Table` primitive across the four JSX walkers + HEEx and the pack templates (server-driven via `paged` + query params where the source supports it, client-side fallback otherwise).
**Decisions (design pass 2026-07-13, maintainer-signed):** (A) route interactive state through page-level `state {}` + the existing `renderStateWrite` seam — no new primitive-local-state seam (invariant #7); (B) **client-side v1** (sort/filter/slice the bound array); server-driven `QueryView`-unwrap is a decoupled slice 2 that auto-upgrades once M-T2.6 flips the scaffold's unbounded `.all` to paged; (C) the 4 JSX targets land together, HEEx pinned in `heex-parity` with a reason (LiveView `handle_event` round-trip is a different topology), Feliz attempted / fail-fast per M-T6.15.
**Client-side column SORT — landed + build-gate-verified on all 4 JSX targets (PR #1890, slices 1–4):**
- The optional `WalkerTarget` seams `renderSortableHeader` + `renderSortedRows` (`src/generator/_walker/target.ts`); `Table(sortKey:, sortDir:, Column(..., sortable:, field:))` in `src/generator/_walker/primitives/table.ts`, **gated** so an un-ported target stays byte-identical.
- **React** (`tsxTarget`) — inline `[...rows].sort` with `as`-cast comparator. **Vue/Svelte/Angular** — a shared `sortRows()` helper (`src/generator/_frontend/table-sort-helper.ts` → `src/lib/table-sort.ts`) because their strict templates reject the inline cast; imported via the `usesTableSort` walker flag (Angular re-exposes it as a `protected readonly` member — templates can't call free imports). Signals/`$state`/`ref` write idioms per target.
- **Verified end-to-end** (not just structural): React (react tsc), Vue (`vue-tsc` + `vite build`), Svelte (`svelte-check` + `vite build`), Angular (`ng build`) all green on a generated sortable-table project. Tests: `test/generator/{react,vue,svelte,angular}/table-sort.test.ts`.
- **Feliz + HEEx** gracefully degrade to a plain (unsorted) table — the seams are absent, so the sort args are ignored (output correct, not broken). Feliz doesn't map cleanly (Elmish `renderStateWrite → "()"`; sort needs Set-Msg/update plumbing + Fable verification); HEEx needs a LiveView `handle_event` round-trip. Both pinned as known sort gaps. *(**HEEx de-pinned** — the LiveView `handle_event` round-trip landed server-driven in slice 8; see the HEEx leg below. **Feliz de-pinned too** — client sort/pager/filter landed in slice 10; see below.)*
- **Scaffold wiring LANDED (slice 5):** `scaffoldList` marks every column `sortable:` with an explicit `field:` and threads `sortKey:`/`sortDir:` into the Table; the List page declares the two string state fields. Scaffold list pages sort out of the box on the 4 JSX frontends. Feliz/HEEx carry the two extra state fields as harmless unused model-fields / mount-assigns (verified: React scaffold `tsc` green, Feliz + Phoenix scaffolds generate).
- **a11y fix (slice 5 follow-up):** the sortable header was a `<span onClick>`, which trips `svelte-check --fail-on-warnings` (the `generated-svelte-build` gate) + axe. Now a real `<button>` (keyboard-focusable, implicit ARIA role, reset chrome) on all 4 JSX targets.
**Client-side PAGINATION — landed + build-gate-verified on all 4 JSX targets (slice 6):**
- New **optional** `WalkerTarget` seam `renderPager(spec)` + `PagerSpec` (page ref, `pageSize`, `totalExpr`); `Table(page:, pageSize:)` in `table.ts` slices rows to the active window (built generically from `renderStateRead`) and appends a Prev / "Page N of M" / Next pager. **Gated** so an un-ported target renders unpaged (byte-identical). The pager total derives from the post-sort array (non-null when sort is active) so no redundant `?? []` guard is emitted (a double guard is a strict-Angular TS2869 error).
- **int-typed page state:** generalized `page()`/`stateBlock()` (`StateFieldSpec`) to carry typed fields + literal inits, and taught the **Vue page-shell** to honour `field.init` (Angular/Svelte/React already did). The scaffold list declares a 1-based `pageNum: int` state (named `pageNum` for readability beside `pageSize`; `page` was a reserved keyword at the time, since made soft in every identifier position — M-T1.3 Defect B) and threads `page:`/`pageSize: 10` into the Table.
- **Verified end-to-end:** React (tsc), Vue (`vue-tsc` + `vite build`), Svelte (`svelte-check` 0-warnings + `vite build`), Angular (`ng build`) all green on generated paged projects. Feliz/HEEx degrade (extra `pageNum`/`sortKey` model-fields, verified generate). Tests: `test/generator/{react,vue,svelte,angular}/table-pagination.test.ts`.
**Server-driven PAGINATION + SORT — landed (slice 9, coordinated with M-T2.6):** the auto-`findAll` is now paged-by-default (`ensureFindAll` → `paged<T>`), so the scaffold list consumes the envelope server-side: `useAll<X>({page, pageSize, sort, dir})` reads `.data.items`, pages off `.data.totalPages`, and sends `?page=&pageSize=&sort=&dir=` to the whitelisted-ORDER-BY route across all five backends. `QueryView paged:` + `Table serverPaged:` gate the unwrap; the client-pager primitive stays valid for non-paged array sources / explicit finds. HEEx unwraps `.items` (sort/pager pinned at the time — **since landed server-driven in slice 8's HEEx leg**, below); Feliz decodes the `items` field (Model stays `'T list`, page 1, pager pinned). **Acceptance e2e landed:** `test/behavioral/pagination.mjs` seeds 1000 rows over the real HTTP surface and asserts the paged window/counters/ORDER BY end-to-end (gated in `behavioral-e2e.yml`).
**The envelope's `total` is reachable from the DSL, on ALL SIX frontends — landed (M-T1.3 Defect B).** `.all` is paged-by-default, so a page that wants the true row count has it in hand; #2324's scoping table recorded it as unreachable and routed around it. Three things were in the way, and the third was the interesting one. (1) A hand-written `QueryView { of: X.all }` is **auto-paged** — the `data:` binding unwraps to `.items` so a body written for a collection keeps iterating records — which put every metadata member one level too deep: `rows.total` emitted `<hook>.data.items.total`, `undefined` at runtime and `TS2339` at build. The rows and the metadata come off different levels of the SAME envelope, so the metadata read is now re-rooted past the unwrap while `rows` stays the array (`items` deliberately is not — on an unwrapped binding `rows` already *is* the array). (2) The two frontends that DECODE the wire rather than hold it now decode the metadata too: **Feliz** splits the envelope into the read's `Remote<'T list>` plus a sibling **`PageMeta` record** (one record, not a field per member, so the carrier can grow without another Model field and another `Loaded` tuple slot), and **Flutter**'s Riverpod provider yields **`Paged<T>`** instead of dropping everything but `items` on the floor. (3) **Paged-ness was being decided in two places.** The walker DERIVED it from the find's return type while both read collectors keyed on the explicit `paged: true` FLAG — so a hand-written paged read had a body resolving `rows.total` against a field its own wire layer never decoded. Both readings were defensible; apart they emit a non-compiling app. There is now ONE derivation (`src/generator/_walker/paged-query.ts`, `isPagedQuery`) with three consumers, which is what makes the disagreement unrepresentable rather than merely fixed. Two latent bugs fell out of unifying it: the Feliz paramless api fn declared `Async<Result<'T list, string>>` while its decoder returned the pair (it had never been reached, because a control-less read was never paged before), and the realtime `Refetch` Msg hop keyed on paged-ness when what it actually preserves is page/sort CONTROLS — a control-less read now refetches inline again. **No frontend gates**, so no `loom.*` code was added: the earlier cut of this work shipped a `loom.paged-member-unsupported-target` for Flutter and for auto-paged Feliz, and closing those two properly made it unreachable. Verified against the real compilers, not the IR: `tsc --noEmit` on generated React (with the pre-fix shape reproducing `TS2339`), `dotnet fable` on both a controlled scaffold and a control-less hand-written app, `flutter analyze` + `flutter build web`. The envelope's **`page` had no spelling at all** — a reserved keyword, so `rows.page` didn't parse. That is the same declarable-but-unreadable class as M-T5.18 Track C's BUG-004 (`e.resource`), so it got the same fix: `page` is now a soft keyword in all six identifier positions (member access, field name, state field, lvalue, nameRef, paramName — the `keyword-identifier-coverage` snapshot pins it), which also makes an aggregate field or page-state field literally named `page` declarable, readable and assignable. Docs: [`page-metamodel.md` §9.2](../page-metamodel.md).
**Client-side FILTER — landed on all 4 JSX targets (slice 7):** a `Table(filter: <stateRef>)` renders a search box ABOVE the table (via the optional `renderFilterInput` seam) and wraps the bound rows in a case-insensitive substring match over `Object.values(row)` (via `renderFilteredRows`), applied BEFORE sort/slice so the pager counts the filtered set. **Gated** so an un-ported target renders no box + unfiltered rows (byte-identical). React inlines the `.filter(...)`; Vue/Svelte/Angular call the shared `filterRows` helper added to `src/lib/table-sort.ts` (their strict templates reject the inline `Object.values` cast — same split as `sortRows`), imported via the new `usesTableFilter` walker flag (Angular re-exposes it as a `protected readonly` member). Two-way binding per idiom: React controlled `value`/`onChange`, Vue `v-model`, Svelte `bind:value`, Angular `[value]`/`(input)` + `$any`. Client-only (gated off `serverPaged` — a server-driven filter is a later slice, like sort/pager's server mode). **Multi-root wrap (found by the local `tsc` build-verify):** the filter box + table are adjacent JSX siblings, illegal in a `QueryView`'s `{cond && (…)}` single-expression slot (`TS2657`). New optional `wrapMultiRoot` seam wraps them in a React `<>…</>` fragment (Vue/Svelte/Angular tolerate multiple template roots → omit the seam, byte-identical). **Scoped to the filter box only** — the pager alone is emitted under a pack wrapper (`<Paper>`) in scaffolded pages, so wrapping it too would add a redundant fragment there (byte-drift on the page-emitter fixture) for no gain; a bare pager-only `QueryView` stays a pre-existing edge. **Build-verified locally against the real compilers:** React `tsc --noEmit` (filter+sort+page), Vue `vue-tsc`, Svelte `svelte-check --fail-on-warnings` all green; Angular gated on CI (`generated-angular-build` — local `ng build` blocked by an env Node patch-version floor, and the change is a no-op for the fragment seam + reuses the ng-build-verified `sortRows` member idiom). Tests: `test/generator/{react,vue,svelte,angular}/table-filter.test.ts` (incl. the filter→sort→slice composition, pager-counts-filtered, and the fragment-wrap assertion). **Client-paging arithmetic is now a SEAM (`renderClientPaging` / `renderServerTotalPages`).** It was built generically in `primitives/table.ts` out of literal JavaScript — `.slice(…)`, `Math.max`, `Math.ceil`, `.length` — which is fine for the four JSX targets (they share JS) but is not source F# or Dart can host. So client paging was structurally unreachable on Feliz/Flutter *however* `renderPager` behaved: porting the five existing seams would still have emitted `.slice(…)` into `App.fs`. The arithmetic now goes through a seam whose DEFAULT is the JS form, so the JSX targets are byte-identical (gated by the four `table-pagination` suites + the page-emitter byte-equivalence fixture) and a non-JS target can express the same window in its own language. **`renderSortedRows` is widened to match**, in the same pass and for the same reason: it sorted by a RUNTIME key (`row[sortKey]`), which JS does natively and F#/Dart records cannot — a statically-typed target has to emit a `match` over the key with one arm per sortable column, and the positional signature carried no column list. It now takes a `SortedRowsSpec` whose `columns` is the `field:` of every `sortable:` Column, pre-scanned from the same resolution `emitColumn` uses so the two can't disagree. The four JSX targets destructure and ignore it. **One shape question is left for the Feliz slice itself, and it is in the PACK rather than a seam:** `primitiveTable` interpolates the header into a string literal (`Html.th [ Html.text "${col.header}" ]`), so a sortable header — markup, not text — needs the pack to take a rendered header child. Reading the emitted `App.fs` settled the rest of the shapes: rows are an F# `'T list` piped through `List.map`, row fields keep DSL casing (`row.name`), Model fields are PascalCase (`model.SortKey`), and `dispatch` is in scope in the view function. **Remaining slices:** (server-driven filter) folds in once a `QueryView`-level filter param exists. The client-side core (slices 1–7, 9), the HEEx leg (slice 8, below), the Feliz leg (slice 10, below) + acceptance e2e are done.
**Server-driven SORT + PAGINATION on HEEx/Phoenix — landed (slice 8, HEEx leg).** De-pins the LiveView half of slice 8 and closes the last product-visible gap in the mission: a scaffolded Phoenix list page was **hard-capped at the first 10 rows** — no pager, no sort, rows 11+ unreachable. Three compounding defects, all found by reading generated output on fresh `main` rather than from the tracker:
- **The `of:` args were dropped.** The scaffold emits `<api>.<Agg>.all(pageNum, 10, sortKey, sortDir)`, but `QueryBinding` carried only `{kind, assign, aggregate}`, so `renderQueryLoadBlock` emitted a bare `list_products()` and the repository's `list/4` defaults pinned the page to 1 forever. `QueryBinding.listArgs` now carries the rendered args (HANDLER position — the load block is a function body, so refs must be `socket.assigns.x`, never the template's `@x`).
- **`StateFieldIR.init` was ignored in the Elixir mount** — the scaffold's `pageNum: int = 1` seeded as `0` (the same defect the Vue page-shell had in slice 6, fixed there and never ported). Latent while the assign was unread; once the value reaches `list/4` it drives `offset = (page - 1) * page_size` negative, which Ecto rejects. New `stateInitFor` (next to `defaultInitFor`, `heex-walker-core.ts`) honours literal inits.
- **`renderTable` parsed away every control arg.** Now emits `sort_key=`/`sort_dir=` on `<.table>`, `sort_field=` on each `sortable:` `<:col>`, and a `<.pager>` below it.
**Server-driven by design, not a port of the JSX client-side approach** — a LiveView calls its context function directly, so sort/page are just arguments to the already-paged `list/4` with its whitelisted `ORDER BY`; the topology that made slices 1–7 awkward on HEEx is an *advantage* for slice 9's server mode. Hoisted `handle_event("loom-sort"/"loom-page")` clauses update the assigns and re-run the same load block `handle_params` uses (sort toggles asc↔desc and resets to page 1; the page event clamps at 1 so a crafted event can't drive a negative OFFSET). `CoreComponents.table` gained a `sort_field` slot attr rendering a real keyboard-focusable `<button>` + `aria-sort` (the a11y call slice 5 made for JSX), plus a new `pager/1` with disabled ends. **Client-side filter stays out of scope** — it is gated off under `serverPaged` on the JSX targets too, and `list/4` has no filter parameter. **Gated:** a Table with no control args, and a page with no such Table, emit byte-identical output. **Verified against the real compiler:** `mix compile --warnings-as-errors` green on a generated scaffold in `hexpm/elixir` — which also exercises LiveView's compile-time `attr`/`slot` validation of the new `sort_field`/`<.pager>`. Tests: `test/generator/elixir/heex-table-controls.test.ts` (load, markup, handlers, CoreComponents surface, and the gated-off case).
**`DataGrid` — the interactive-grid ceiling, React (slice 10; PRs #2294, #2306).** Slices 1–9 took `Table` as far as it goes portably: ONE sort column, ONE substring filter, prev/next paging — hand-rolled per target because the shapes are simple enough to be. Multi-column sort, per-column filters and column visibility are **row-model** concerns, so a fourth and fifth interactive mode on `Table` would mean hand-rolling a row model six times over. New `DataGrid` primitive instead, on **TanStack Table** (the library shadcn's own DataTable recipe uses).
- **Emits a hoisted child component, not inline markup.** `useReactTable` is a hook and a DataGrid almost always sits in a `QueryView`'s `data:` slot — which the walker emits as a *conditional expression*, where hooks can't run; the hook can't move up to the page either (it needs the lambda's `rows`), and a component declared inside the page would remount on every render and lose its sort state. New `WalkResult.hoistedModuleDecls` channel (created EAGERLY on the root ctx — child contexts are `{...ctx}` spreads, so a lazily-created array on a nested ctx is one the root never sees) spliced between imports and the page component. The child is generic (`<T extends object>`) so no DTO type name is resolved in the walker.
- **Chrome from the pack, wiring from the walker.** `primitive-data-grid.hbs` on **mantine** (#2294, lead pack) then **shadcn / mui / chakra** (#2306) — each renders its own table chrome while the TanStack half above it stays byte-identical across packs. MUI deliberately uses its presentational `<Table>`, not its own DataGrid engine: forking the row model per pack is the thing this architecture exists to avoid.
- **Row selection** (`selection: <string[] state field>`) is the one piece of grid view-state the page can read — a sibling "Delete selected (3)" has a real need for it, while sort/filter/visibility are opaque. TanStack's selection map stays in the child; the page owns the id list in `state {}` and a `useEffect` bridges them through a setter passed as a prop. The checkbox column is **walker**-emitted (plain `<input type="checkbox">`) rather than a pack component — it's the one cell whose *behaviour* is load-bearing — so selection needed no template change in any pack and ports unchanged. Fixed en route: an `array`-typed page-state field emitted `useState<any>(undefined)` (now `useState<string[]>([])`), and a page with BOTH `state {}` and a hook-bearing primitive emitted **two** `from "react"` import lines (a duplicate-identifier error) — the shell now drains the walked body's react specifiers into its own line.
- **Honestly gated, not silently degraded.** `loom.datagrid-unsupported-target` makes DataGrid on a non-React frontend a compile error pointing at `Table`; `loom.datagrid-selection-not-state` / `-not-array` reject a `selection:` binding the walker would otherwise drop or mistype. Pinned in `heex-parity` + `allowlist-ratchet` with reasons; `showcase.ddd` and the `REQUIRED_PRIMITIVES.tsx.core` flip are deliberately **deferred to the cross-framework port** (`tsx.core` is required of EVERY pack, and `showcase.ddd` is built by the Vue matrix — flipping either now trips this mission's own gate).
- **Verified against the real compiler** per pack: generate → `npm i` → `tsc --noEmit` clean on mantine, shadcn, mui, chakra. Tests: `test/generator/react/data-grid.test.ts`, `data-grid-packs.test.ts`, `test/ir/datagrid-{unsupported-target,selection}.test.ts`. Docs: [`page-metamodel.md` §9.1](../page-metamodel.md).
**`DataGrid` on Vue (slice 10b).** Generalises the primitive into a real `WalkerTarget` seam and ports it, so the grid is no longer React-only.
- **New `renderDataGridChild` seam** + `WalkResult.hoistedComponentFiles`. React's same-file module hoist does not carry over: a Vue SFC and a `.svelte` file compile to exactly ONE component each, so those targets return a whole `src/components/<Name>.vue` and register it in `usedUserComponents` — reusing the depth-correct component import the page shell already emits (a scaffold page two directories deep gets `../../components/…`). Arg parsing, column resolution and the component name stay shared; the reactive idiom, the TanStack package and the file container are the target's. The React extraction was gated **byte-identical** on the selection fixture, `acme.ddd` and `showcase.ddd`.
- **Vue rides `@tanstack/vue-table`** with the adapter's documented getter idiom (`get data()`, `get sorting()`), one `applyUpdater` helper for TanStack's updater-or-value union, `FlexRender` for simple columns, and a `watch(rowSelection)` that emits `selectionChange` into the page's ref. Packs: `vuetify@v3` + `shadcnVue@v1`.
- **Cells render in the TEMPLATE on Vue,** keyed by column id: a TanStack `cell` function must return VNodes and the walker produces markup. So Vue's packs take `headerBody`/`cellBody` fragments from the walker — the same split `Table` already uses on Vue, whose sortable header is likewise walker-emitted.
- **Found by compiling the output — a shipped React bug.** A `Column` with a formatting accessor emitted `cell: () => <Badge>{row.name}</Badge>` with `row` **unbound**, so any such grid failed `tsc`. It shipped in #2294 because the tests asserted the sort/filter flags without ever compiling that case, and no CI matrix example has a computed-cell DataGrid. Both targets now bind the row through one confined cast (`dataGridRowVar` seam + a `CellRow` alias); regression tests added on both.
- Also fixed: Vue's page shell emitted `ref([])` for an array state field (`Ref<never[]>`, so any assignment is a type error) — the Vue twin of the React/Svelte gap #2294 closed. And the pack's grid components are now imported into the SFC, not the page, which would fail `vue-tsc` under `noUnusedLocals`.
- **Verified against the real toolchain:** `vue-tsc --noEmit` + `vite build` green on generated projects for **both** Vue packs and for the computed-cell case; React re-verified with `tsc --noEmit`. Tests: `test/generator/vue/data-grid.test.ts`.
**`DataGrid` on Svelte (slice 10c) — and the adapter that didn't exist.** `@tanstack/svelte-table` (the official adapter, stable at 8.21) peers on `svelte: ^4 || ^3.49`: it predates runes, and the generated stack is Svelte 5. Svelte 5 support ships only in `9.0.0-beta`, and TanStack v9 is a different API (`createTable` + a `_features` array, no row-model functions) — so taking it would have made the Svelte grid behave differently from React's and Vue's, the exact divergence this architecture exists to prevent. There is no maintained Svelte-5 fork (`svelte-headless-table` is Svelte 4; `@vincjo/datatables` is Svelte-5-native but a different library entirely).
- **Resolved by dropping one layer, not by taking a beta.** The target drives **`@tanstack/table-core`** directly — the framework-agnostic package every official adapter wraps, on the same v8 API React and Vue use, with *no framework peer dependency at all*. Runes supply the reactivity the adapter would have, which is precisely what the adapter's own code does with a store. Same behaviour on all three frontends, no pre-release in a user's `package.json`.
- **Every state slice is controlled, including `pagination`.** The table is rebuilt inside `$derived.by`; that is only correct because nothing uncontrolled is left to lose — an uncontrolled `pageIndex` would silently reset to 0 on every sort click (caught in the spike, before any emitter existed). It is also what makes the markup reactive: `table-core` mutates its own internals, so reading the runes inside the derivation is the dependency edge Svelte needs. `table-core` also demands `onStateChange` + `renderFallbackValue` in resolved options, which the adapters normally supply.
- Child lands at `src/lib/components/<Name>.svelte` via `hoistedComponentFiles`; `renderSveltePage` now returns `{ content, componentFiles }` (one call site) rather than growing a 19th positional out-param. Cells render in the markup keyed by column id, same split as Vue. Packs: `flowbite@v1` + `shadcnSvelte@v1`.
- **Verified against the real toolchain:** `svelte-check --fail-on-warnings` **0 errors / 0 warnings** + `vite build` green on generated projects for **both** Svelte packs and for the computed-cell case. Tests: `test/generator/svelte/data-grid.test.ts`.
**`DataGrid` on Angular (slice 10d) — and the gates the staged rollout was holding open.** Angular rides the stable `@tanstack/angular-table` (`createAngularTable`, peers `@angular/core >= 17`), so no adapter problem; what diverges is everything around it. The child is a decorated CLASS at `src/app/components/<kebab>.component.ts`, and a standalone component needs BOTH an import line and an `imports: []` entry — threaded through the Angular walker sink, not `usedUserComponents` (that channel is for extern components rendered via `NgComponentOutlet`). Page state is a SIGNAL, so the selection write is `.set($event)`; a bare assignment compiles and silently never updates the view. Templates evaluate against the instance, so `String`/`Math`/the row cast are re-exposed as members. The row type is concrete (`CellRow`) rather than generic — `strictTemplates` would otherwise have to infer the parameter at every tag use-site. Packs: `angularMaterial@v1` + `primeng@v1` + `spartanNg@v1` (all three differentiate through `loom-*` classes, exactly as their `primitive-table.hbs` already does, so the markup is shared).
- Also fixed: Angular's page shell emitted `signal([])` for an array state field (`WritableSignal<never[]>`, so every `.set(...)` is a type error) — the fourth and last instance of the gap #2294 opened on React, then Vue, then Svelte.
- **`ng build` now runs locally.** Angular 22 floors at Node `^22.22.3` and the sandbox shipped 22.22.2, which is why the earlier `Table` slices were CI-gated only; installing 22.23.2 side-by-side closed that, so this slice was verified the same way as every other — real toolchain, before pushing.

**Gates retired now that all four JS frontends ship it.** `primitive-data-grid` joins `TSX_ONLY_PRIMITIVES`, so it is REQUIRED of the tsx / svelte / vue / angular formats (and, since slice 10e below, of `feliz` — heex/flutter stay honest gaps). `showcase.ddd` gains a `ProjectsGrid` page exercising multi-sort, per-column filters, column visibility and `string[]` row selection, and the temporary `SHOWCASE_EXCLUDED_PRIMITIVES` entry is gone. Two bugs surfaced immediately from putting it there, which is exactly what the showcase fixture is for:
- **A name collision the derived-name guard missed.** `page ProjectsGrid` + `testid: "projects-grid"` both derive `ProjectsGrid`, and React hoists the child into the page's OWN file → `Duplicate function implementation`. The guard now rejects page names as well as user-component names (`pageRoutes` is the available view of "names this module binds", so no new plumbing through `walkBody`'s parameter list).
- **The playground page-builder round-trip** canonicalizes a primitive to brace-builder form, so the showcase grid is written `DataGrid { … }` rather than `DataGrid(…)` — the walker accepts both, but only one round-trips.
- Verified with the REAL CI gate rather than an approximation: `LOOM_REACT_BUILD_CASE=examples/showcase.ddd:<pack>` green on all four React packs.

**`DataGrid` on Feliz (slice 10e) — and the Flutter decision, now recorded.** This closes the mission's last open item. It was NOT "port it to two more targets": the question was whether either target can host the *actual* row model, and the two answers differ.
- **The test is "can it host TanStack", not "does it emit JSX".** `DataGrid` is a TanStack row model, so the only way to add a target without forking behaviour is to run the same library there. **Feliz can:** Fable compiles F# to JavaScript, so it binds **`@tanstack/table-core`** — the framework-agnostic package every official adapter wraps, already the Svelte target's choice — through ordinary Fable interop (`[<Import>]` / `[<Emit>]`, the same escape hatch the toast and EventSource bindings use). The row model executing on Feliz is byte-for-byte the one React/Vue/Svelte/Angular execute. **Flutter cannot, permanently:** there is no Dart adapter and no Dart port, `dart:js_interop` exists on Flutter *web* only, and the shipping target (what `generated-flutter-build.yml` builds) is a native APK with no JS runtime. A web-only primitive that compiles on one Flutter target and not the other is worse than an honest gap. `Table` stays the portable answer there. The rationale is now a recorded decision — [`D-DATAGRID-TARGETS`](../decisions.md) plus the code comment in `src/util/flutter-deferred-primitives.ts` — not a backlog item, and `loom.datagrid-unsupported-target` says *why* per target rather than "not supported yet".
- **A `[<ReactComponent>]` child in `App.fs`, reached via `moduleDecl`.** Feliz renders through React, so `React.useState` is available — but not in a `QueryView`'s `data:` slot, which Feliz emits as a lambda passed to `View.remoteList` (a conditional call inside the page's `view`). So the grid is a hoisted child, using React's `moduleDecl` shape rather than Vue/Svelte's sibling `file` (an F# module holds many declarations). `index.ts` splices the declarations after the wire layer and before the page views — F# is order-sensitive.
- **The row is projected at the CALL SITE, which is what removes the generics problem.** The walker deliberately resolves no DTO type name (the JSX children are generic over the row type) and F# has no structural typing to stand in for that. So the page — where the row list is fully typed — projects each row into a plain JS object: one key per `accessorKey` column, plus a `loom-cell-<id>` **lazy `unit -> ReactElement` thunk** per computed column, closing over the typed row. Cell markup stays lazy (only visible rows render) and no type name reaches the child.
- **Projected values are RAW, deliberately — parity beat "better".** Fable maps `decimal`/`money` to a Decimal object whose `valueOf()` returns a string, so `a < b` is lexicographic. Normalising to a JS number was the obvious fix and is the WRONG one: the JSX frontends parse money into a `decimal.js` Decimal with the same string `valueOf`, so normalising would have changed both the sort order *and* the default sort direction (`getAutoSortDir` branches on `typeof value === "string"`) relative to the other four. Raw gives Feliz identical semantics. **The money-sort weakness is real and shared across all five frontends** — a cross-target defect to fix once, not to fix unilaterally on the fifth. (Fixed as follow-on B below.)
- **`selection:` is the one slice that reaches the page,** and on Feliz it cannot be a direct write: `renderStateWrite` is a no-op because Elmish state lives in `update`. `DataGrid` joins `BOUND_INPUT_PRIMITIVES` so the grid dispatches `SetSelectedIds`, and `boundSetMsg`/`boundSetArm` learned an ARRAY payload (`string list`) — they previously only spelled `bool` or `string`.
- **Two shipped bugs fixed en route, both found only by running the output** (the pattern this mission keeps re-learning):
  - **`table-core` does not merge its own default state.** `getState()` returns the RAW `state` option, so a state carrying only the controlled slices throws inside `getHeaderGroups()` (reading `columnPinning.left`) and the grid renders **nothing**. The framework adapters spread `table.initialState` in; the two adapter-less targets must do it themselves. **The shipped Svelte grid had exactly this defect** — reproduced end-to-end on a generated project, `svelte-check` and `vite build` both green — so the fix landed on Svelte too, sourcing the defaults from one throwaway instance.
  - **The Svelte grid did not build at all on the `flowbite` pack.** `import { type Table } from "@tanstack/table-core"` collides with flowbite-svelte's `Table` **component** — a duplicate declaration, a hard parse error in the Svelte preprocessor rather than a type-only clash. Now aliased to `TanstackTable`.
- **`<array>.length` was typed as `string` in the IR** (only the `string`-receiver case had an arm), so a `{xs.length}` interpolation skipped the `convert` the lowerer inserts for non-string parts. JS frontends coerced it silently; Feliz emitted `"Selected: " + xs.Length`, an F# type error. Fixed in `lower-expr.ts`, plus a small optional `renderMemberRead` seam so F# can spell `.Length` (JSX targets omit it → byte-identical).
- **Verified against the real toolchain, runtime included:** `dotnet fable` + `vite build` green on all THREE Feliz CI apps (showcase, scaffold-parity, auth-gate), and a new `scripts/feliz-data-grid-smoke.mjs` drives the previewed bundle in headless Chromium asserting **behaviour** — multi-sort (shift-click, with tie-breaking), a per-column filter narrowing rows, a hidden column's cells disappearing, `aria-sort`, a computed cell's markup rendering, and selection round-tripping through the Elmish Model into a sibling's `Selected: N`. Wired into `generated-feliz-build.yml` alongside the existing smokes; the five pre-existing Feliz smokes re-run green. Tests: `test/generator/feliz/data-grid.test.ts`, `test/ir/datagrid-unsupported-target.test.ts`.
**Follow-on A — a hoisted grid child must import what its CELLS need (fixed).** Reported at the end of the Feliz slice as a Svelte-only `ReferenceError`; building a repro on each frontend showed it was wider. A computed column's markup is walked with the PAGE's import map and then emitted into the hoisted component FILE, so the imports and the code landed in different files. **Vue, Svelte and Angular all emitted a child calling `formatDateTime` with nothing providing it**, and Svelte additionally referenced an unimported pack component (`<Badge>`) — a runtime `ReferenceError` with `svelte-check` and `vite build` both green. React and Feliz were immune only because their cell markup stays in the page's own module.
- New `DataGridSpec.cellImports` — the delta of the walker's import map across column resolution. **Additive**: the names stay on the page too, because a missing import breaks the app and a spare one does not (the generated tsconfigs keep `noUnusedLocals` off for exactly this reason), and removing one risks stripping a name a later sibling needs.
- Merged with `packImports` **per source** by a shared `mergedImports` helper: the grid chrome and the cells routinely name the same module, and two import lines for one module is a duplicate-declaration error, not a style nit.
- Format helpers reach markup with no registration channel at all, so they are not in that delta on every frontend — Vue's page shell imports the whole surface unconditionally, Angular re-exposes the used ones as members. Both now do the same in the child, against **one shared list** (`_frontend/format-helpers.ts`) replacing the literal each emitter spelled out. That duplication is how three frontends drifted into the same gap.
- Also fixed en route: Angular's page shell never re-exposed `String` as a component member, so any page interpolating a numeric value failed `ng build` with "Property 'String' does not exist" (surfaced by the `array.length` typing correction above; the grid child had always lifted it).
- **Verified build AND runtime per frontend:** `vue-tsc` + `vite build`; `svelte-check --fail-on-warnings` 0/0 + `vite build`; `ng build`. Then each bundle was served and the first row's cells read back — identical on all three, where Svelte previously rendered nothing at all.

**Follow-on B — money sorted lexicographically on every frontend (fixed).** The cross-target defect the Feliz slice recorded rather than fixing unilaterally. `money`/`decimal` reach the row as a Decimal OBJECT — `decimal.js` on React/Vue/Svelte, Fable's on Feliz — and **both wrappers' `valueOf()` returns a STRING**, so a bare `a < b` compares the decimal text: an ascending sort came out `[10, 100, 9]`. Confirmed against real `table-core` + `decimal.js` before writing any fix.
- **It was never DataGrid-only.** `sortRows` (the shared client-sort helper `Table` calls on Vue/Svelte/Angular) and React's inlined equivalent had the identical `(av as number) < (bv as number)`, so the *portable* primitive — the one `loom.datagrid-unsupported-target` points authors at — was wrong too. Both now normalise through `Number()`, which goes through that same `valueOf` and is therefore the correct numeric read; non-objects, arrays and NaN pass through untouched so string and boolean columns keep their ordering.
- **DataGrid gets an explicit `sortingFn` on money columns only.** Overriding every column would fork TanStack's own `text`/`alphanumeric` choice for strings; `Number()` (not `alphanumeric`) is the comparator because digit-chunk comparison is wrong for negative amounts.
- **Typing the column needed a new channel.** A page body carries no `receiverType`, so `o.amount` inside a `data: rows => …` lambda types as `string` for *every* field — the accessor cannot say which column is money. The enclosing `QueryView` knows, so it now records its row aggregate (`WalkContext.listRowAggregates`, resolved through `tryDetectApiHook` — `singleAggregateOfQuery` unwraps a method-call receiver and returns `"all"` for a list query) and the primitive reads the declared field types off it. Unresolvable → no override, i.e. the previous behaviour.
- **Angular was already correct and stays so:** its DTO layer keeps money as a plain `string`, so TanStack picked `alphanumeric` and ordered numerically. The explicit comparator agrees (`Number("9.00")` is 9) and makes all five uniform.
- **Verified at runtime on all five frontends** with amounts where text and numeric order disagree (9, 10, 100): every one now sorts `9 → 10 → 100` ascending and reverses on the second click, DataGrid and `Table` alike. Test: `test/generator/_frontend/table-sort-decimal.test.ts` EXECUTES the emitted helper rather than asserting on its text — a string-level assertion is what let this ship.

**Follow-on C — `Table` on Flutter was a bare `DataTable`, and the scaffold did not compile (fixed).** The gate message promised "`Table` sorts and pages on every frontend"; on Flutter it did neither. `flutter-target.ts` implemented neither `renderSortableHeader` nor `renderPager`, and `primitives/table.ts` degrades SILENTLY when a seam is absent — so `sortable:` rendered a plain header and `page:` rendered nothing, on the target that message is shown to most.
- **Server-driven, matching the Phoenix rationale.** A Flutter list read is now a Riverpod **`.family` keyed by the query record** (`(page, pageSize, sort, dir)`), so a sort or page tap is just a state write: the key changes, Riverpod refetches, the server orders and windows. A record, not a class — `.family` compares keys by `==`, and a class without a hand-written one would miss the cache and refetch forever. The provider returns a `LoomPage<T>` (rows + `totalPages`), which is what the pager needs and what a bare `List<T>` could never express.
- **Four independent compile breaks in the scaffolded output, none of which CI could see** — `generated-flutter-build.yml` only ever built a HAND-WRITTEN showcase, so no `with scaffold(...)` app had ever been compiled. `flutter analyze` on one reports: a **JavaScript object literal emitted into Dart** (`productAllProvider({ page: … })` — the shared walker hard-codes the query bag's spelling, now the `renderQueryArgsBag` seam); the read hoisted **before** the `state` binding it reads (`referenced_before_declaration` — Dart is not hoisted); **unbound route params** (a declared `:id` resolves as an ordinary param ref and was emitted with nothing declaring it); and a **comment where a Widget was required** (`<Widget>[ /* … */, ]` — Flutter's children are comma-separated, so the diagnostic sentinel has to be a valid expression).
- **Also fixed:** `DataRow.key` takes a `LocalKey?`, not the `Key` the pack emitted; the pack stringified a sortable header's WIDGET into `Text('InkWell(…)')` (it ignored `headerMarkup`); `notifier` went unbound for a body whose only state writes come from Table controls; and the client-paging default leaked `Math.max`/`Math.ceil`/`.slice` into Dart once a pager existed — now `skip`/`take`, with a typed `switch` comparator for client sort (Dart has no `row[key]`, which is exactly why `SortedRowsSpec` carries `columns`).
- **The gate now has the leg it was missing.** `generated-flutter-build.yml` gains a scaffold-parity app held to the same `analyze` + `test` + `build web` bar. Runtime behaviour is proven by `scripts/flutter-table-controls-test.dart`, a widget test that taps the real generated controls and asserts the real Notifier state — **Flutter web renders to canvas**, so the Playwright DOM smoke that proves the Feliz leg is not available and `flutter test` is where behaviour is provable. It pins: tapping a header sets key+asc, re-tapping flips to desc, Next/Prev move the page, Prev disables on page 1, and "Page 1 of 5" comes from the server's `totalPages`.
- **Verified against the real SDK** (Flutter 3.44.8): `flutter analyze` **0 errors** and `flutter build web --release` green on BOTH the scaffold app and a hand-written sorted/paged `Table` app, plus the widget test passing.
- **Not done, and the message no longer claims it:** client-side FILTERING (`filter:`) is still dropped on Flutter — `renderFilterInput`/`renderFilteredRows` are unimplemented. HEEx has no client filter either (it is gated off under `serverPaged` on the JSX targets), so `loom.datagrid-unsupported-target` now promises sort + pagination only.


**Slice 10 — the Feliz leg: client sort + pagination + filter (M-T1.1 tail closed).** Feliz was the last frontend rendering a STATIC table. Slice 9's seam work cleared two of the three obstacles; the third was in the pack, and a fourth surfaced only once the F# was generated:

- **Client-paging arithmetic** → `renderClientPaging` / `renderServerTotalPages` (landed in the prep pass). Feliz windows by INDEX (`List.indexed |> List.filter |> List.map snd`) rather than `List.skip`, which RAISES when the skip count passes the list length — the exact shape a last-page click produces. The page count is integer ceiling division (`(len + size - 1) / size`); F# has no `Math.ceil` over an int quotient.
- **Runtime sort key** → `SortedRowsSpec.columns` (landed in the prep pass). The target emits `match model.SortKey with | "name" -> compare a.name b.name | … | _ -> 0`, comparing the FIELD rather than a stringified value — so an `int` column orders numerically, matching JS's relational `<` instead of the lexicographic order a `string`-keyed sort would give.
- **The string-literal table header** → a `headerMarkup` flag on the walker's column shape. `primitiveTable` wrapped every header in `Html.text "…"`, which would have emitted the clickable sort button as a *string literal*. The flag is set by the walker (never sniffed from the header text, so a label of `"(net)"` stays a label), and only the Feliz pack reads it — the markup packs splice either form into the same `<th>` slot.
- **Sibling roots don't concatenate in an expression language** (found by generating, not by reading). The primitive joined the filter box / table / pager with a newline, which IS composition in JSX but is a SEQUENTIAL expression in F# — it would have discarded the filter box and returned only the pager. New optional `joinRoots` seam: Feliz builds a real `Html.div [ prop.children [ … ] ]`; the four JSX targets omit it and stay byte-identical (a plain table never reaches it on any target).

The MVU plumbing came for free as predicted: `BOUND_INPUT_PRIMITIVES` widened from name→ONE bind-arg to name→LIST, and `Table`'s `sortKey:`/`sortDir:`/`page:`/`filter:` refs now flow through the same `collectPageBoundState` → `boundSetMsg`/`boundSetArm` path a `Field(bind:)` uses — including the string→int parse arm `page` needs (the pager stringifies the new page number on the way in). Selecting a NEW sort column dispatches twice (`SetSortKey` then `SetSortDir "asc"`), which Elmish folds in turn; no combined Msg case was needed.

**One documented divergence:** the JSX filter searches `Object.values(row)`; Fable has no dependable runtime value enumeration for an F# record, so Feliz searches the columns the table DISPLAYS (`FilteredRowsSpec.columns`, the field of every column with a simple member accessor). Narrower than every row value — named here rather than left to be discovered.

**Server-paged mode is now ON (M-T2.6 Feliz leg — the follow-on slice).** The Feliz wire decodes the paged envelope's `totalPages` into a SIBLING int Model field rather than widening the list field to the envelope — the list field is also read by `View.idOptions` (FK selects) and by the realtime refetch, so an envelope there would break both for no gain. `renderPagedEnvelopeMember` (which replaces the old `pagedDataIsList` boolean) resolves the scaffold's `rows.items` to the binding and `rows.totalPages` to that sibling; a controlled `.all` read takes `(page, pageSize, sortKey, sortDir)` and sends `?page=&pageSize=&sort=&dir=` (the sort pair only once a column is selected — `?sort=` would ask the backend to order by a column that doesn't exist); and the `Set<Field>` arms for the controls bind the UPDATED model first, so the request carries the new page/sort rather than the one it replaced. **The refetch rides the sort DIRECTION arm, not the key** — a header selecting a new column dispatches key-then-direction, so refetching on both fired two requests per click with a window where the later ARRIVAL (not the later request) won; the header's dispatch order is pinned by a test because the single-refetch rule depends on it. The realtime handler dispatches a `Refetch<Field>` Msg instead of issuing a read, since it runs outside `update` and would otherwise have to guess the page and sort. **Paged-ness and CONTROLLED-ness are separate:** a `QueryView paged: true` whose `of:` threads no controls still reports the true count but leaves `Next` disabled — a pager that navigated there would write page state no request reads, which is the same silent failure. Verified by `scripts/feliz-scaffold-paging-smoke.mjs`, which asserts the QUERY STRINGS the app sends (a pager that renders and a pager that pages are indistinguishable in the DOM against a stub) — including that one click produces exactly one request.

**How server-paged mode was first found to be broken, and why the finding stands.** Implementing `renderPager` made the SCAFFOLDED list page — which is server-paged — emit `rows.totalPages`, and the Feliz wire decodes only the envelope's `items` into a plain `'T list`. `dotnet fable` rejected it outright ("The type `List<_>` does not define … `totalPages`"), which is the *loud* half. The sortable header was the SILENT half of the same bug: it compiles, writes sort state, and nothing refetches on it — an interactive control that does nothing. New `serverPagedControls` target flag (`false` on Feliz, omitted everywhere else) suppresses both, so a server-paged table renders the plain, server-ORDERED page the backend already sent; `collectPageBoundState` skips a `serverPaged` `Table`'s refs to match, so no dead `Set…` Msg arms are emitted either. Scaffolded output is `diff -rq` byte-identical to `main`. `renderServerTotalPages` stays implemented, so flipping the flag is the only change once the Feliz envelope unwrap lands (M-T2.6's remaining Feliz leg). **Worth noting how this was caught:** the hand-written showcase page passed locally; the CI matrix's *scaffold parity* app is what failed. A per-frontend build gate that generates both a hand-built and a scaffolded app is doing real work.

**Verified against the real toolchain, and at RUNTIME.** `dotnet fable` compiles the emitted F# clean, `vite build` bundles it, and a new Playwright smoke (`scripts/feliz-table-smoke.mjs`, wired into `generated-feliz-build.yml` alongside a `ProductTable` showcase page) drives the previewed bundle with a stubbed list response and asserts the RENDERED ROWS after paging, sorting and filtering — the page window and its clamping, Prev/Next disabled states, ascending/descending on both a string and a numeric column, and the filter narrowing the rows AND the page count. The sibling `feliz-smoke.mjs` runs backend-less, which leaves a table with no rows to act on; stubbing the response is what makes the controls testable without a server. Tests: `test/generator/feliz/table-controls.test.ts`.

Vue/Svelte/Angular gained a `DataGrid` compile cell (#2375 — the grid child previously had no build gate at all), and the DataGrid pager chrome is translatable (#2371). ## M-T1.3 — Charts & the dashboard ceiling — `partial` (reconciled 2026-08-05 — the phase ledger below had gone stale while [the scope doc](./missions/M-T1.3-charts-and-dashboards-scope.md) stayed current) · **L** · P1/P2
A minimal `Chart` primitive (line/bar over a collection expr). Keep the set closed and small; HEEx renderer required or pinned (heex-parity gate).
**Scoping pass landed — [`missions/M-T1.3-charts-and-dashboards-scope.md`](./missions/M-T1.3-charts-and-dashboards-scope.md).** Verified on fresh `main` by generating and compiling, the mission is **data-first, not rendering-first**: four defects sit under the chart ask, three of them `tsc`-provable build breaks that no gate catches today because no example exercises the surface.
- **Defect A — collection ops don't survive the JSX walker.** `QueryView { of: Order.all, data: rows => Stat { "Total", rows.count } }` parses with 0 errors and emits `orderAll.data.items.count` → `TS2339: Property 'count' does not exist`. `walker-core.ts:1428` emits member access verbatim; there is **no `isCollectionOp` arm anywhere on the JSX path** (React/Vue/Svelte/Angular all break; **Feliz is correct** — `fs-expr.ts:121` maps `count → List.length`; Flutter's `DART_LEAVES` has no arm).
- **Defect B — a client-side KPI over `.all` is page-scoped.** `.all` is `Paged<T>` by default (M-T2.6, `enrichments.ts:1685`, `pageSize: 20`), so the count would read `20`. The true value is `data.total`, already parsed and typed in the envelope, and **unreachable from the DSL**.
- **Defect C — the singleton aggregating projection silently mis-emits.** `projection SalesTotals { orders: int  from Order as o  select orders = count }` validates clean and emits a **`SELECT *` whole-table load + every row rehydrated into a domain object + a free identifier `count`** (`TS2304: Cannot find name 'count'`) returned as an *array* for a singleton. `projection-checks.ts:185-200` claims this surface is *"HONESTLY REJECTED … rather than silently mis-emitted"*; the gate doesn't fire because Hono **has** ported the query-time emitter and the *"singleton-whole-table-aggregation refinement lands WITH that emit"* (`:198`) did not.
- **Defect D — there is no ui→projection read path at all** (the load-bearing gap). `QueryView { of: Sales.SalesTotals, data: r => Stat { "Total", r.orders } }` validates clean and emits `/* unresolved: Sales */ undefined.SalesTotals.isLoading` — a runtime `TypeError` *and* a build break. Structural, not a typo: `lower-ui.ts` has **no projection arm**, and `_frontend/api-module.ts` emits **no client** for a projection route. Angular ships a `primitive-modal-controlled` template per pack; Flutter, whose dialogs are imperative, bridges through a generated `LoomModalHost` widget (rising-edge `showDialog` + dismissal reported back so page state stays authoritative). Both had the SAME root cause on top of the missing renderer: their `renderModal` target seam claimed the primitive with a comment before the shared `emitModal` could try the controlled shape. The slot-coverage gate's waiver list is now EMPTY — every target renders every slot. The untranslatable-text inventory pinned by `test/generator/_walker/i18n-slot-inventory.test.ts` is being drained slice by slice; the two entries that were genuinely **authored `.ddd` prose** now ship. **`Icon { label: … }`** is how a meaning-bearing glyph opts out of decorative-by-default — an accessible NAME, so it rides the existing D-I18N-ATTR pair (the HTML fragment for the 15 `.hbs` packs, the target-native value for Feliz/Flutter), which also retired the last two hand-rolled copies of the decorative-vs-named decision in those packs. **`CodeBlock { title: … }`** is a caption in text position (the `Card` title's shape); the code SOURCE is deliberately NOT a slot — translating code breaks it, and an untitled block therefore leaves a page string-less. Doing this exposed that **HEEx had no attribute-position localization at all**: it translated every TEXT slot and zero ATTRIBUTE ones, so a control's accessible name shipped in English at every locale while the caption beside it translated. `localizedHeexAttr` is that missing half (HEEx's `{pgettext(…)}` expression syntax rather than `<%= … %>` — which is exactly why `elixirI18nString` already escaped `{`/`}`), and it retro-fixes the `buttonAria` slot too. The three attribute helpers in `i18n-emit.ts` (`localizedNamedAttr` / `localizedAriaLabelAttr` / `localizedNamedValue`) each carried two branches where the TEXT-position localizer carried three: literal → `t()`, anything else → raw expression. The missing middle was the ICU-template branch, so ``Button { icon:, label: `Delete {p.name}` }`` emitted `("Delete " + p.name)` — while the extraction pass still wrote `"Delete {name}"` into the catalog under a key nothing resolved. The branch is now factored once (`icuTranslateCall`) and shared by all four helpers. **Pack-DECLARED chrome — the English that only ever existed in a `.hbs` (landed).** The five slices above drained chrome the EMITTER builds and hands a template as a ready token. That design cannot reach the other half: a string a pack invents on its own would need a curated key in the toolchain, a token in the emitter's view model and a threading argument at every call site, for a word only that pack renders. Two of the fifteen packs spell the empty picker "— select —" rather than "Select…"; vuetify alone labels its breadcrumb landmark; the shadcn dialogs carry a visually-hidden "Close". None of those belong in a shared table. So a pack now **declares** its strings in `pack.json` and spells them through four Handlebars helpers bound into every `pack.render` (`src/generator/_packs/pack-chrome.ts`, wired at the loader so partials see them too, and documented in [`design-packs.md` §2 `chrome`](../design-packs.md)):
- **Declaration, not a scrape.** Scraping `.hbs` cannot tell `Remove` from `VariantProps`, an `@doc` string or a class name, gives an author no opt-out, and — the real objection — produces no **role**, which is what makes two occurrences of "Close" in one pack distinguishable to a translator. A declaration is also the only form that can be VALIDATED (a message containing `<`, `"`, `\` or a non-ICU brace is rejected at pack LOAD, naming the pack, because the i18n-OFF path splices it unquoted) and gated.
- **`pack.<family>.<role>.<hash>`**, per D-I18N-KEY. FAMILY, not `family@version`: mantine v7 and v9 spell "Remove" identically and a translator should translate it once — and when two versions *do* diverge the content hash separates them by itself, which is the whole reason the message is hashed rather than the version pinned. Exercised in the shipped packs: flowbite's "Select…" and chakra's "— select —" are the same ROLE and land on different keys.
- **Four helpers, because the position is what diverges.** `{{{chrome …}}}` (markup text, ICU hole values as hash args), `{{{chromeAttr "aria-label" …}}}` (a WHOLE attribute — a bound attribute changes shape per framework: Vue's `:` prefix, Angular's `[attr.…]`, HEEx's `{…}` body, so the template cannot spell the name itself), `{{{chromeValue …}}}` (a target-language value — a toast argument, a `??` fallback), and `{{{chromeImport …}}}` for a WHOLE-FILE template, whose specifier is the pack's to give since only it knows where its file lands relative to the runtime.
- **The import is the part that isn't uniform,** and it split cleanly in three. A whole-FILE template writes its own (`format-helpers` → `src/lib/format.*`; shadcn's `components/ui/dialog`). A FRAGMENT walked into a page is wired by asking the RENDERED body for the binding's prefix — the same honest question the hoisted-`DataGrid`-child renderers already ask, because whether the chrome appears at all is the active pack's call. An operation-form MODULE is neither: it is a pack fragment spliced into the page but rendered by the page shell, *after* the import block was serialized on React and Svelte — so the form wiring now runs before that serialization rather than after it. HEEx needs no import in a layout (`html_helpers`), but `core_components.ex` is a plain `use Phoenix.Component` module, so its `chromeImport` emits the `use Gettext, backend: …` that puts `pgettext/2` in scope.
- **Wired across every one of the 13 families / 17 pack directories:** the array field's `Remove` / `Add {item}` / `(arrays not yet supported in forms)`, the op dialog's `This operation has no parameters.` and its `{operation} succeeded` toast, `Yes`/`No` in every `format-helpers`, `Choose file`, the empty picker option, vuetify's `Breadcrumb` landmark, the shadcn/shadcnVue dialog `Close`, and on HEEx `Home` / `Actions` / `Pagination` / `No items.` / the flash `close`. All of it flows through the SAME `buildUiCatalog`/`buildMessageCatalog` the page strings use, so `.loom/messages.en.json`, each app's `locales/en.json`, the Phoenix `.pot`/`.po` and `ddd i18n extract/sync/status` carry it with no new plumbing — the system-level catalog resolves each ui's pack from `deployable.design` (model-derived, so the codegen-free CLI extractor reaches it too).
- **i18n-OFF is byte-identical BY CONSTRUCTION, not by reconstruction:** the binding starts OFF and each helper returns the bytes the template previously spelled inline (`chromeImport` returns nothing), and a frontend switches it on only under the already-enabled gate — so pack chrome never flips the runtime on for a string-less app (verified: an app with no authored text keeps `{}` for its catalog, no `i18n.ts`, no `intl-messageformat` dep, and a raw `>Yes<`).
- **Two gates, both mutation-proved** (`test/generator/pack-declared-chrome.test.ts`): every declared role must be rendered by some template in the SAME pack (the dead-catalog class M-T1.11 already drained once for authored slots), and — the one that makes this hold — a scan of EVERY `.hbs` for user-visible English in a markup text node or a user-facing attribute, with a ratcheting waiver list of seven reasoned non-strings (TypeScript generic fragments, a SvelteKit placeholder token, Elixir code inside a HEEx attribute). Reverting any wired string fails both, naming the file and the string. Without that scan the next pack template to hardcode a word ships untranslatable and nothing says so.


**ICU INTERPOLATION on Phoenix HEEx now ships** (D-I18N-HEEX-ICU), closing the last frontend that could not translate a sentence with a hole in it — it emitted the very shape the `loom.user-visible-concat` validator BANS in `.ddd` source (`<%= "Status: " <> @code %>`). The message stays **ICU verbatim** so the Phoenix `.po` carries the same msgid as the other five catalogs, and the two jobs split at their natural seam: gettext resolves the message, `ex_cldr_messages` formats the holes in whatever the active locale's translation turned out to be. The emitted call nests that way round — `loom_icu(pgettext(<key>, <ICU msgid>), [<holes>])`. Rewriting ICU to gettext's `%{}` grammar at emit time was rejected: it is cheaper but breaks the one-message-per-key invariant and loses the `,format` set and plural/select outright. A **second-tier gate** keeps the CLDR compile off apps that don't interpolate — read off the extraction pass's per-entry `icu` marker, not a `{`-sniff, because merged pack chrome carries holes (`chrome.pageOf`) that HEEx never renders through this path; a literal-only Phoenix app is byte-identical, verified by generation. Documented degradation, measured not assumed: `ex_cldr_messages` implements ICU MessageFormat but **not** ICU number skeletons (`::currency/USD` — the spelling Loom's own grammar documents) and raises on a `date` style with no `ex_cldr_dates_times`, so an unformattable message degrades to raw hole substitution rather than crashing the render — the Flutter runtime's `_substitute` trade, for the same reason. Plural and select DO work. **Follow-up — the one slot the sweep found still falling through** (#2437 covered `Text`/`Heading`-shaped slots; a later sweep of all 18 `USER_VISIBLE_SLOTS` for gate-vs-emission agreement found `toolbarAria` was not among them): HEEx `Toolbar` carried its `{role:"toolbar", needsName:true}` fallback name as a hardcoded `extraAttrs` entry and had no `labelAsAriaLabel`, so an authored `label:` fell through the generic named-attr branch to a bogus `label=` attribute on the `<div>` — raw `<>` concat when interpolated, and the hardcoded English "Actions" left as the accessible name even for a plain literal. It also flipped the ICU gate on, compiling the whole CLDR engine to format a hole it then rendered by concatenation. Fixed by giving `Toolbar` the flag and making `extraAttrs` **defaults rather than overrides** (a derived attribute suppresses the same-named contract entry — otherwise the tag carries two `aria-label`s and the default outranks the authored name). HEEx-only: the other five frontends were each verified to already bind it. Note the gate that missed it — `user-visible-slot-coverage.test.ts` asserts the sentinel appears ANYWHERE in the page, which the leaked `label="…"` attribute satisfied; it cannot distinguish "rendered as the accessible name" from "dumped into a meaningless attribute".

## M-T1.20 — Frontend surface gaps: the five rejections outside the pack matrix — `open` · **M** · P2
