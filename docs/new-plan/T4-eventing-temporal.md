# T4 — Eventing, workflow & temporal

*Weak-spot #4: scheduling was the language's temporal hole — no timers, no jobs, no saga deadlines. `timerSource` Phases 1 + 2 now close the timer half on all five backends (in-process scheduler + advisory-lock single-fire, plus durable Postgres-backed `cron:` drivers with store-coordinated single-fire, retry, and coalesce-once missed-run catch-up; only timezone/overlap sugar + saga deadlines still pending). Deployables are no longer pure runtime islands: external-broker transport (M-T4.4) is **done** — Redis (`broadcast`/`ephemeral`), RabbitMQ (`queue`/`ephemeral`+`queue`/`work`), and Kafka (`broadcast`/`log`+`queue`/`work`) all ship on all five backends, plus service-to-service broker auth and a k8s broker subchart (`src/generator/_channels/bindings.ts` `SHIPPED_COMBOS`; the elixir kafka leg rides `brod`, `src/generator/elixir/channels-emit.ts`; `src/system/helm.ts` `renderBrokerTemplate`). Two honest gaps remain: redis provisions only `broadcast/ephemeral` (no `queue/ephemeral` — rabbitmq is the only queue-capable transport for that combo, per `SHIPPED_COMBOS`), and elixir has no `last_event_id` consumer-side dedup (ack-reliant, same stance as java). The `test:channels*` e2e suite is CI-wired via `channels-e2e.yml` (`run-channels` label; #2386 fixed the "subscribed must mean the broker said yes" readiness defect across all five backends, #2336 its elixir leg). The saga/workflow core is otherwise solid and at full 5-backend parity.*

## M-T4.1 — `timerSource` (scheduling) — `partial` · **XL** · P1 (design-first)
The temporal hole. Time as an event source: a system-scope `timerSource` binding emitting tick events; workflows react via existing `on(e)`/`create(e) by` triggers — zero new workflow grammar (the `schedule every 5m {}` shape was explicitly rejected). Phase 1 (in-process scheduler + advisory-lock single-fire) AND Phase 2 (durable per-backend `cron:` drivers) are both landed on **all five backends**; only timezone/overlap sugar + saga deadlines remain.
**Phase 1 landed — all five backends:** grammar (`timerSource` SystemMember + `DURATION` terminal + system-wide `for:` scope), `TimerSourceIR`, cadence validators (`loom.timer-cadence` AST-level; `loom.timer-event-shape`/`-needs-state`/`-source-unbound` IR-level), print arm, obs catalog (`timer_fired`/`timer_skipped_overlap`/`timer_lock_contended`/`timer_emit_failed`). Owner derived from `migrationsOwner` (no stamp); byte-identical where unused. Per-backend driver, all sharing the tx-scoped `pg_try_advisory_xact_lock` single-fire (same FNV-1a→int32 key, so cross-backend replicas contend on one key) and dispatch through the existing in-process saga dispatcher:
- **Hono/node** (#1963) — `scheduler.ts`, node-cron (`cron:`) / setInterval (`every:`). `examples/timers.ddd`.
- **.NET** (#1986) — `TimerService : BackgroundService`, Cronos / `PeriodicTimer`, EF Core `SqlQuery<bool>`.
- **Java/Spring** (#1987) — `TimerScheduler @Component`, `@Scheduled(cron)` / `@Scheduled(fixedRate)`, `TransactionTemplate`. No new Gradle dep.
- **Python/FastAPI** (#1988) — `app/scheduling.py`, APScheduler `CronTrigger` / `IntervalTrigger`, `apscheduler>=3.10,<4`.
- **Elixir/Phoenix** (#1989) — one GenServer per timer, `Process.send_after` (`every:`) / `Crontab.Scheduler` (`cron:`, conditional `{:crontab}`); serialized GenServer loop makes overlap structurally impossible (no `timer_skipped_overlap`).
**Phase 2 landed — durable `cron:` drivers, all five backends.** A `cron:` timer becomes a durable, Postgres-backed job (store-coordinated single-fire across replicas + retry + coalesce-once missed-run catch-up); `every:` (sub-minute) timers stay the in-process advisory-lock path. Each backend uses its ecosystem's Postgres-native store; every driver was prototyped against Postgres, then runtime-verified on the *generated* stack (boot → cron fires → tick dispatches → saga persists; first-boot baseline + pushed-back-watermark catch-up asserted). Adds the `timer_catchup` obs event.
- **node/Hono** (#2009) — pg-boss (`boss.schedule`/`boss.work`, retryLimit 3) + a self-owned `loom_timer_runs` watermark for coalesce-once catch-up (pg-boss cron has no native backfill).
- **.NET** (#2101) — Hangfire + Hangfire.PostgreSql; standard cron, auto-schema, native overdue-on-start missed-run; `IRecurringJobManager`.
- **Java/Spring** (#2112) — JobRunr core (no SB4 starter → manual `JobRunrConfig`: SQL `StorageProvider` + background server + `scheduleRecurrently`).
- **Python/FastAPI** (#2132) — procrastinate `@app.periodic` tasks; the `periodic_defers` table is the store-coordinated single-fire + native coalesce-once catch-up ledger; worker runs in-process in the lifespan. Deps swap apscheduler → `procrastinate` + `psycopg[binary]`.
- **Elixir/Phoenix** (#2135) — Oban; a scheduler GenServer enqueues unique (per-boundary) Oban jobs (`unique` = the single-fire ledger, never re-runs a boundary) + a `loom_timer_runs` watermark for coalesce-once catch-up.
**Remaining:** timezone `in:` + `overlap: allow` sugar; Phase 3 (`missed: run`/`retry:` surface syntax, per-env cadence, saga-deadline sugar, `ddd verify` join); **a permanent timers-e2e runtime leg** — every timer runtime proof to date is a per-PR hand-run (#1963, #2009, #2525's watermark-advance boot), so a regression in fire/single-fire/catch-up behaviour has no standing gate; the M-T6.23 slice-3 work also measured `every:` timers firing from BOTH replicas on both node adapters (the advisory lock prevents concurrent, not sequential, double-fire — the at-least-once note below is the honest contract, but "single-fire across replicas" phrasing elsewhere over-claims for sub-minute timers).
**Runtime-verified (Hono, docker postgres):** the timer fires on cadence → tx-scoped `pg_try_advisory_xact_lock` (single-fire; no lock leak under concurrent load — the fix over a plain session lock, which leaks the unlock across pooled connections) → tick dispatched through the in-process channel dispatcher → `create(t) by t.<id>` reactor creates one saga instance per tick → persisted + readable via `/api/workflows/.../instances`.
**Note — reactor correlation:** a tick reaches a workflow only through a `channel` carrying it, and workflow event-consumers require an id-shaped correlation field; the scheduler mints tick fields (`newXId()` / `new Date()`), so `create(t) by t.<id>` spawns one instance per tick. Relaxing correlation for stateless recurring `on(t)` is a Phase-2/3 consideration.
**Note — delivery is at-least-once:** the advisory lock is a mutex around the body (no concurrent double-fire), but clock-skewed peers can fire sequentially, so reactors must be idempotent. Exactly-once-per-instant (durable claim / competing-consumer) is deferred to Phase 3 — not needed for the at-least-once contract.

## M-T4.3 — Outbox & delivery completion — `partial` · **M** · P2
**Re-audited on fresh main 2026-07-27 — the roadmap line was largely stale; the M-T4.4 broker mission (slices 7a–7d) delivered most of it.** What now ships:
- **Transactional outbox on all five backends** — the shared `__loom_outbox` table (`outboxTableShape`, emitted whenever a hosted context has a `retention: log|work` channel), a write-tee recording durable events in the caller's transaction, and a polling relay draining them. node/dotnet/python have the **standalone (no-broker) path too** — the relay dispatches drained rows to the in-process dispatcher when no `channelSource` broker is bound.
- **Elixir relay exists** — an `OutboxRelay` **GenServer** poll loop over a `LoomOutbox` Ecto schema (`channels-emit.ts`), *not* Oban (the roadmap's "Phoenix/Oban relay" was wrong on both counts).
- **Dead-letter surface + obs events** — `event_dead_lettered` (outbox row exhausting `MAX_ATTEMPTS`) and `channel_dead_lettered` (broker DLQ); both in the `_obs` catalog.
- **Opt-in knob decided + wired** — it's `retention:` on the channel (`log|work` ⇒ durable outbox, `ephemeral` ⇒ at-most-once). The richer `OutboxConfig` publisher-mode rule stays a proposal.
- **S5(d) closed** — the outbox→broker upgrade path the DDD review asked for ("make it real when brokers land") is built on all five backends.

**Genuinely remaining (precise, fresh-main pointers):**
1. **Standalone (no-broker) durable outbox — Java + Elixir landed** (this mission): a `retention: log|work` channel *without* a `channelSource` now gets the crash-safe in-process outbox node/dotnet/python have.
   - **Java** — `LoomEventOutbox` (@EventListener) records durable events in `__loom_outbox` inside the producer's tx (generic Jackson map — the row round-trips java→db→java, no wire codec); the reactor's inline `@EventListener` is DROPPED (`DispatchCtx.localDurableEvents`); `LocalOutboxRelay` (SmartLifecycle poll) drains and invokes the reactor methods directly, threading the outbox row id on `OutboxDelivery` so the `last_event_id` marker dedups. Gated on no-broker only (one relay, no race). **Runtime-proven** (gradle JDK 25 bootJar + docker postgres): `place()` → `OrderPlaced` recorded (`dispatched=t`, `attempts=0`) → `Fulfil` saga instance created post-commit via the relay.
   - **Elixir** — the emit seams route through the standalone `<App>.Channels` tee: a durable event → `record_durable/2` (Ecto insert into `__loom_outbox`), ephemeral → local dispatch; `LocalOutboxRelay` (GenServer poll) drains → `decode`s the row → parks the row id on the process dictionary (the saga marker dedups) → broadcasts to the hosted context Dispatchers (the subscriber handles it, others no-op via the catch-all). Choreography re-emits ride the outbox. **Runtime-proven** (`mix phx.server` via the hex-mirror harness + docker postgres): `place()` → `OrderPlaced` recorded in `__loom_outbox` (`dispatched=t`, `attempts=0`) → `Fulfil` saga instance created post-commit via `LocalOutboxRelay` (decode → broadcast to the dispatcher); `mix compile --warnings-as-errors` clean.
   - Both: choreography re-emits ride the outbox on the next drain; ephemeral / channel-less projects are byte-identical.
2. **`last_event_id` idempotent-consumer markers — Java + Elixir landed** (this mission), closing the 7c/7d residuals. Where a deployable hosts a durable channel's context AND a saga consumes it, at-least-once redelivery becomes effectively-once (parity with node/dotnet/python):
   - **Java** — the JPA saga-state entity maps `last_event_id`; a new `OutboxDelivery` ThreadLocal carries the envelope id (= outbox row id) that the `ChannelConsumerService` parks around each dispatch; the saga handler compares/stamps it. Gradle-compiled JDK 25.
   - **Elixir** — the saga-state Ecto schema maps `last_event_id`; the `ChannelConsumer` parks the envelope id in the process dictionary before `route/1`; each `create`/`on` handler no-ops on a redelivery of the recorded id (`Process.get(:loom_event_id)`) and stamps it before the state save. `mix compile --warnings-as-errors` clean on plain Ecto/Phoenix.
   - Foreign consumers keep the ack-semantics stance; ephemeral-only / channel-less projects are byte-identical (both backends).
3. **LISTEN/NOTIFY over polling** — unimplemented on every backend (all relays poll at 500 ms).
4. (Minor) node outbox is Drizzle-only (MikroORM gap). ⚠ *verify first* — `emitMikroOutboxMachinery` (`platform/hono/v4/workflow-builder.ts:1327`) emits the mikro half of both exports, so this line may be stale.
5. **The write-path atomicity ruling — the one genuinely undecided question here** (added 2026-08-30 from the [08-24 review](../audits/generator-code-review-2026-08-24.md)'s register rows 2/3 + §D5; ledger rows `G2667-C4` / `G2667-C5` / `G2667-D5`). The transactional capture seam exists and works where a write tx exists — but three shapes sit outside one, and they were fenced rather than decided:
   - **mikroorm's save path opens no transaction at all** (`typescript/emit/mikroorm.ts:2358-2371` — `em.fork({keepTransactionContext:true})` + upsert + association + containment saves + event dispatch, no `em.transactional`), so outbox atomicity structurally cannot hold on that adapter even though `recordDurable` is wired. The drizzle sibling wraps in `db.transaction` (`repository-save-builder.ts:241,251`). The TS document / embedded / event-sourced adapters share the shape.
   - **Workflow-step / extern-handler / timer emits insert outbox rows outside any transaction** on node — deliberately fenced, with the reason in the emitter (`platform/hono/v4/workflow-builder.ts:1239-1244`: "the non-transactional fallback (relay re-entry, timer / workflow emits that have no enclosing write tx)"). Whether a workflow's own state write should share a transaction with its emits is the undecided part.
   - **.NET document and event-sourced repositories dispatch durable events after commit** (`dotnet/emit/repository.ts:867-881` and `:1082-1103`: `SaveChangesAsync` then `foreach … DispatchAsync`), so a crash between the two loses the event with the write already durable.
   Related asymmetry to settle in the same ruling: java's explicit command handlers are class-`@Transactional` while .NET/node commit per `SaveAsync` (§D5) — a partial-write window java does not have. **Design first, then drain**: state the rule (which writes and which emits share a transaction, and what a shape with no write tx does instead), then make each backend implement it. This is an owner decision, not an emitter bug.

>
> **The contract, decided and written into `src/ir/util/realtime-rooms.ts`:**
> - **RULE 1** — a realtime stream inherits its deployable's auth mode. The SSE route is an ordinary authenticated route: on no backend's bypass list, 401 without credentials.
> - **RULE 2** — the stream carries the **same credential as an ordinary API call** from the same frontend, and no other: the HttpOnly `session` cookie the `/auth/callback` handshake issues, sent by `withCredentials: true` — the `EventSource` twin of the api client's `credentials: "include"`. The gate is the *same* `auth: ui` × `auth: required` × declared `user { }` predicate, exposed as `realtimeStreamCredential(deployable, target, user)`; `auth: none` stays byte-identical.
>
> **Why the cookie beat the query-param token.** The SPA never sees the raw token (auth.md "Session depth": all access/refresh tokens ride HttpOnly cookies), so a token channel would need a *new* mint endpoint and a *new* token type on all five backends; a URL-borne credential lands in access, proxy and `Referer` logs; and four of the five backends (.NET, Java, Python, Phoenix) **already** accept the `session` cookie alongside `Authorization: Bearer`, while every backend already emits `Access-Control-Allow-Credentials: true`. The cookie cost one constructor argument on the client and one cookie read on one server.
>
> **The node outlier.** Verify-first found a second live hole behind the first: Hono's OIDC verifier read **only** the `Authorization` header (`src/platform/hono/v4/auth-emit.ts`, shared by `node@v5`), so on node even a credentialed stream 401s — and, since the emitted api client authenticates by cookie too, so does every ordinary SPA fetch once the base is cross-origin (which the generated compose makes it: `VITE_API_BASE_URL: http://localhost:8080/api`). It now reads the `session` cookie, minimal and identical in shape to the other four.
>
> **What landed:** the contract + `realtimeStreamCredential` in the plan; `withCredentials: true` in the shared `renderRealtimeClient` (react / vue / svelte / angular) and in feliz's `[<Emit>]` shim; node's cookie fallback. Generator gate: `test/generator/_frontend/realtime-stream-auth.test.ts` (16 assertions — per-frontend credentialed + `auth: none` byte-identical control, the node cookie read, and the five gate cases). Runtime gate: `test/e2e/auth-oidc-e2e.test.ts` and `auth-oidc-compose-e2e.test.ts` now open `GET /api/realtime/events` uncredentialed (→ 401, RULE 1) and with `Cookie: session=<real Keycloak token>` (→ 200 `text/event-stream`, RULE 2), plus `/auth/me` by cookie; the shared fixture `test/e2e/fixtures/auth-oidc-e2e.ddd` grew a `delivery: broadcast` channel so the SSE route is emitted. Every fix was mutation-proved (revert → the named assertion fails).
>
> **Still open under this ID:**
> 1. **Flutter** — handed off, not fixed. Its SSE call `loomEventSource(apiUri('/realtime/events'), …)` takes no credential, and both transports are const strings (`REALTIME_SOURCE_WEB_DART` / `_IO_DART`). But the blocker is upstream: flutter's *ordinary* API calls are bare top-level `http.get/post` with no `BrowserClient..withCredentials` and no cookie jar, so there is **no credential path for the stream to inherit** — fixing only the stream would be theatre. The exact change: (i) give flutter an authenticated http client (`BrowserClient()..withCredentials = true` on web; a cookie jar or a bearer store on native), (ii) thread the credential into `renderFlutterRealtime` and emit `web.EventSource(uri.toString(), web.EventSourceInit(withCredentials: true))` in the web transport, (iii) decide the native story — an HttpOnly cookie cannot exist on a mobile client, so native needs a bearer the IO transport puts on the request, which is a *different* credential and therefore a plan amendment, not a port.
> 2. **The (a) conformance test across all five backends** — RULE 1 is asserted at runtime on node only. A cross-backend emitter test that every SSE route sits behind the auth plug (and is absent from every bypass list) is still unwritten.
> 3. **The durable-tee half of (a)** (§A9 — "a durable event tees to the hub at write time, not at relay drain") is untouched by this packet; it stays with M-T4.3.
> 4. **A browser-level runtime leg** — nothing yet drives a real `EventSource` from an authenticated SPA and reads a frame. The runtime legs above prove the server accepts the cookie the client now sends; that `withCredentials: true` attaches it is `EventSource` spec behaviour, pinned only by the generator assertion.


Minted 2026-08-30 from the [08-24 generator review](../audits/generator-code-review-2026-08-24.md) §F4, plus its follow-up register row 20 (re-verified on `main` @ `aa236ae`; ledger row `G2667-F4` in open PR #2668). Two halves, one seam.

**(a) The contract.** §A4 (elixir's `:sse` pipeline had no Auth plug) and §A9 (.NET durable events stopped reaching the SSE wire) were both "one backend re-decided a cross-backend rule on its own". `src/ir/util/realtime-rooms.ts` is already the shared plan — it derives the room key and the tenant claim — but it says nothing about **stream authentication** or **where a durable event tees**. Both fixes landed as per-backend edits, so the next backend edit can silently diverge again. The plan should state, and a conformance test should assert across all five: *a realtime stream inherits its deployable's auth mode*, and *a durable event tees to the hub at write time, not at relay drain*.

**(b) The half that is still a live hole.** With §A4 fixed, elixir now 401s an unauthenticated stream exactly as node's `authMiddleware` and python's `AuthMiddleware` do — and the shared frontend client emits a **bare** `new EventSource(\`${API_BASE_URL}/realtime/events\`)` with no credentials at all (`src/generator/_frontend/realtime.ts:54`). No `withCredentials`, no token in the query string, and `EventSource` cannot set an `Authorization` header by construction. So on an `auth: required` deployable **every** generated SPA — react, vue, svelte, angular, feliz, flutter — now fails to connect, on every backend. (LiveView is unaffected: it re-renders server-side through the authorized read.) [M-T1.10](T1-ui-frontend.md) records this as "an app-config concern, not emitted-client code"; that framing predates the A4 fix and is corrected there.

**The work (design first — this is a wire decision, not a bug fix):** pick ONE cross-backend credential channel for the stream and emit both halves of it. The two honest candidates are a cookie the auth flow already sets (`withCredentials: true` on the client + CORS credentials on the five servers) and a short-lived token minted by an authenticated endpoint and passed as a query param (which every backend's auth middleware must then accept for that route only). Whichever wins becomes a line in the realtime plan, not five independent emitter choices — that is what (a) buys. Note `auth: none` deployables must stay byte-identical.

**Verification when it lands.** The conformance test from (a) over all five backends; plus a runtime leg that connects an authenticated SPA to a live stream and reads one frame — [M-T1.10's ledger row](../audits/generator-code-review-2026-08-24.md) `M-T1.10-realtime-no-runtime-e2e` records that realtime has **no** runtime e2e on any backend today, which is precisely why an auth hole and a delivery regression both shipped green.
