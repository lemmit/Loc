## Finding 1 (new) — Flutter silently drops a user component; the gate that exists for exactly this excludes Flutter

**Severity: P1 silent gap. Not in the 251-row ledger of open PR #2668, not in
`KNOWN_FLUTTER_GAPS`, not in `test/ir/user-component-deferred.test.ts`.**

Reproduction, verbatim from the matrix probe:

```
$ # web/src/examples/store-showcase.ddd, deployable webApp retargeted to platform: flutter
web_app/lib/pages/cart_page_page.dart:
  const SizedBox.shrink() /* unknown layout component: CartSummary */,
```

`component CartSummary()` (`store-showcase.ddd:74`) reads `Cart.count` and calls
a store action. `src/generator/flutter/component-emit.ts:86` defers any
store-bearing component ("reaching it needs a `WidgetRef` — which only the page
path's `ConsumerWidget` carries"), so the component never enters
`ctx.userComponents` and **every call site renders an empty box**. Validation
passes clean — no diagnostic of any severity.

The gate for precisely this class exists and works:

```ts
// src/ir/validate/checks/ui-checks.ts:2095
const COMPONENT_FILTERING_FRAMEWORKS = new Set(["feliz", "angular"]);
```

Flutter is missing from the set, and `test/ir/user-component-deferred.test.ts`
types its matrix as `framework: "feliz" | "angular"` — so the gate's own
completeness test cannot notice. Feliz refuses the same file honestly; Flutter
degrades silently. Same input, two different failure modes, one of them invisible.

`component-emit.ts` documents **five** deferral conditions. One is gated
(`hasAsyncEffectAction` → `loom.flutter-async-effect-unsupported`). The other four
are ungated:

| Deferral | Site | Gated? |
|---|---|---|
| `usesStores` — reads a store field / calls a store action | `component-emit.ts:86` | **no** — proven above |
| `usesRouteId` — a `byId(id)` read | `component-emit.ts:84` | **no** |
| stateful **and** read-bearing (`ConsumerStatefulWidget`) | `isReadConsumer`, `:139` | **no** |
| `derivedNeedsShell` — a `derived` reaching a store / route id / `currentUser` | `:161` | **no** |
| `hasAsyncEffectAction` — `match await` in a component action | `:154` | yes |

**Fix shape** (small, and the precedent is already written): add `"flutter"` to
`COMPONENT_FILTERING_FRAMEWORKS`, write `flutterDeferrals` beside
`felizDeferrals` / `angularDeferrals` covering the four rows, widen the test
matrix's `framework` union, and pin one arm per row against the emitter's real
output. This is the `§F3` hand-enumerated-collector class the repo's own
generator review names: the set is maintained by hand, so a third filtering
framework joined the codebase without joining the set.

**Root-cause note worth more than the fix:** the gate's completeness test derives
its matrix from a hand-written union type, not from "which emitters filter". A
gate whose scope is a literal cannot ratchet. The durable version asks each
frontend's component emitter whether it filters, the way `WALKER_PRIMITIVES`
asks each primitive whether it has a `heex` renderer.

## Class A — live capability gaps (~12 of the 41 `gap` rows)

`src/diagnostics/unsupported-register.ts` holds **50 rows: 41 `gap`, 9 `scope`**
(counted with `scripts/quality-delta.mjs countOpenGaps`). Reading each row's own
`what` text against its emission site splits the 41 three ways:

**Live — a shipping target genuinely can't do it (~12):**

| Code | The gap |
|---|---|
| `loom.dapper-unsupported` | aggregating query-time projection over a document/event-sourced source; hierarchical (deep/global) tenancy scope filter; declared migration steps |
| `loom.mikroorm-unsupported` | primitive/enum scalar-array root field under relational/embedded; abstract base owning `contains`; declared migration steps |
| `loom.find-predicate-unsupported` | any find/retrieval/projection/capability-filter predicate outside the dapper+mikroorm SQL subset (EF Core + Drizzle lower it in full) |
| `loom.vanilla-document-unsupported` | elixir `shape: document` residue — provenanced ops, derived-field predicates, cross-aggregate deref, VO/private/service/resource calls, reference collections |
| `loom.frontend-collection-op-unsupported` | **every stdlib collection op except `map`** in any page/component/store expression — on all six frontends. `rows.count`, `rows.where(λ)`, `rows.sum(λ)` are hard errors |
| `loom.toast-message-unsupported` | `toast(<expr>)` outside a five-shape v1 subset — all three realtime renderers, arm-for-arm identical |
| `loom.datagrid-unsupported-target` | `DataGrid` on phoenixLiveView (Flutter is a settled never, D-DATAGRID-TARGETS) |
| `loom.store-lifetime-target-unsupported` | a persisted store field with no total F# (feliz) or Dart (flutter) codec — and the two covered sets differ, so a `persist:` store portable between them does not exist |
| `loom.feliz-async-effect-unsupported` | `match await` in a Feliz component host, or on a non-instance subject |
| `loom.flutter-async-effect-unsupported` | `match await` in a Flutter component action |
| `loom.audited-returning-operation-unsupported` | `audited`/`provenanced` × a RETURNING operation on node |
| `loom.java-*-unsupported` (×2) | entity-typed projection / workflow-instance row fields on Java — defensive backstops, likely unreachable |

The two loudest for a product that sells a "no-code feel":
**`frontend-collection-op-unsupported`** (you cannot write `orders.count` in a
page body on any frontend) and **`vanilla-document-unsupported`** (the Elixir
document shape is the one shape-adapter crossing still meaningfully behind).

**Not debt (~5 rows):** `context-filter-unsupported`,
`persistence-mode-unsupported`, `polymorphic-id-ref-unsupported`,
`ui-realtime-unsupported`, `remote-api-op-unsupported` — these are misuse errors,
configuration mismatches, or semantically impossible references wearing a
`-unsupported` suffix. They are not work; slice 2 of M-T9.27 renamed 19 such rows
out of the register and these five look like the same class one pass later.

**Latent (~24 rows):** the gate exists, the feature ships on every target it
names, and no shipping target can trip it (`SUPPORTED_UNION_BACKENDS`,
`PROJECTION_*_SUPPORTED`, `CHART_FRAMEWORKS`, `FIELD_MASK_BACKENDS`, …). These
are the seam a *new* target would gate on. The register's own header explains
this and the rows are kept deliberately. They should not be counted as backlog —
and the fact that **21 of the 31 codes in the diagnostic-firing `UNCOVERED` list
are exactly these latent rows** confirms it: they are uncovered because they are
unreachable, not because nobody wrote a fixture.

## Class F — what the coverage still hides

Three structural blind spots, all of which mean a green board can still be wrong:

1. **`E2E_LESS_CORPUS_FIXTURES` = 12** and growing (was 9 on 08-17). It grows
   *honestly* — new compile-tier witnesses register rather than pretend to a
   runtime leg — but the effect is the same: 12 features are proven to *generate*
   and *compile*, never to *run*. Two are drainable today on their own entry
   text (`policy-document` and `lifecycle-guard` both cite a multi-principal
   harness that has since landed).
2. **Flutter and Feliz have no runtime leg at all** (`M-T9.38`). Both compile
   green; neither is ever booted. Finding 1 above is precisely the shape that
   slips through: it compiles, it analyzes clean, and the widget is just missing.
3. **CI's post-merge blind spot is unchanged.** `tenancy-e2e`, `*-obs-e2e`,
   `*-oidc-e2e`, `auth-oidc-compose-e2e` never run on an unlabeled PR. The merge
   queue that would close this is **workflow-complete and inert** — GitHub offers
   merge queues only on org-owned repos and this one lives under a personal
   account. That is an admin action, not an engineering one, and it is the
   cheapest single quality win available.

## Caveats on this audit

- **Generate-time OK ≠ compiles ≠ runs correctly.** My 519/522 result proves the
  pipeline produces output without crashing or refusing. It says nothing about
  whether that output compiles (the per-backend Docker compile tiers own that) or
  behaves correctly at runtime (the behavioural/e2e legs own that, and 12 corpus
  features have no runtime leg at all). Docker was available in this environment
  but the compile tiers were not run.
- **The corpus tests features one at a time.** Every crossing bug in Class D was
  found by the *pairwise* corpus, not this one — feature × feature is where the
  remaining silent bugs live, and that corpus is young.
- **The live/latent/not-debt split of the 41 `gap` rows is a reading**, not an
  execution. I classified each row against its own `what` text and its named
  gate set; I did not construct an input for each row to prove it fires. The
  diagnostic-firing census (`UNCOVERED` = 31) is the mechanism that would.
- **`examples/sales-ui.ddd` does not parse** — correctly and loudly documented as
  a historical prototype in three places and pinned in
  `test/system/ddd-source-census.test.ts`. Not a finding; recorded so the next
  sweep does not re-report it.
